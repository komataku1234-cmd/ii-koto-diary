# Vercelとは(学習メモ)

Next.jsを作っている会社(Vercel社)自身が提供している、Webアプリのホスティングサービス。
「サーバーを自分で用意して立てる」代わりに、コードをGitにpushするだけで自動的にビルド・公開してくれるプラットフォーム。

## 1. 基本的な仕組み

- **Gitと連携する**: GitHub(今回のリポジトリ)を接続すると、pushするたびに自動でビルド・デプロイが走る
- **環境が3種類ある**
  - **Production**: 本番ブランチ(通常`main`)にpush/mergeすると自動でデプロイされる、実際にユーザーが見る本番環境
  - **Preview**: `main`以外のブランチにpushしたり、PRを作ったりするたびに、**そのブランチ専用のURL**が自動で発行される。本番に影響を与えずに動作確認できる(今回のプロジェクトで言う`develop`ブランチへのpushも、これに該当する)
  - **Local(Development)**: 自分のPC上での開発。`vercel env pull`で、Vercel側に設定した環境変数を手元の`.env.local`に取り込める
- 1つのプロジェクトにつき、初回だけは(どのブランチからでも)Production扱いのデプロイになる。それ以降は上記のルール通り

## 2. デプロイの流れ(概要)

1. Vercelにアカウント登録し、GitHubリポジトリを連携する(ダッシュボードから「Import Git Repository」)
2. Next.jsプロジェクトは**設定不要で自動検出**される(ビルドコマンド`next build`、出力なども自動)。`pnpm-lock.yaml`があればpnpmを使ってインストールしてくれる
3. 環境変数(後述)を設定する
4. 「Deploy」を押す、または対象ブランチにpushすると自動でビルドが始まる
5. 数十秒〜数分でURLが発行され、そこでアプリが動く

CLIを使う方法もある(`npm i -g vercel` → `vercel login` → `vercel`で対話的にデプロイ)。

## 3. 環境変数の設定

Vercelのダッシュボードの「Settings → Environment Variables」で、`.env`に書いていたようなキーと値を登録する。

- Production用・Preview用・Development用で、**それぞれ別の値を設定できる**(例:本番用DBとテスト用DBを分ける、といったことが可能)
- 今回のプロジェクトなら`DATABASE_URL`と`ADMIN_PASSWORD`をここに登録する必要がある
- ローカルの`.env`ファイルはgit管理外(`.gitignore`対象)なので、Vercel側には**自動では反映されない**。手動でダッシュボードに入力するか、CLIの`vercel env add`で追加する

## 4. データベースをどう繋ぐか(要注意ポイント)

**Vercelは自分自身ではPostgreSQLサーバーを持たせてくれない。**Vercelが動かしているのは「コード(Next.jsアプリ)」だけで、今Docker Composeで動かしているようなPostgreSQLコンテナのようなものは、Vercelの環境の中には存在しない。

なので、本番用のPostgreSQLは**別のホスティングサービスを用意する必要がある**。Vercelは「Marketplace」という仕組みで、外部のDBサービスをワンコマンドで契約・接続できるようにしている。

```bash
vercel install neon      # PostgreSQL(Neon)
vercel install supabase  # PostgreSQL(Supabase)
vercel install upstash   # Redis等(Upstash)
```

これを実行すると、そのDBサービスに新しいDBインスタンスが作られ、接続用の環境変数(`DATABASE_URL`など)が**自動でVercelプロジェクトに設定される**。

以前「Vercel Postgres」という、Vercel自身がPostgresを直接提供する機能があったが、現在はこの形(Neonなど専門のDB会社と提携し、Marketplace経由で使う)に変わっている。

## 5. このプロジェクト(ii-koto-diary)で必要になりそうな作業

学習優先とのことなので、あくまで「後で実際にやること」のメモとして。

1. GitHubリポジトリ(`komataku1234-cmd/ii-koto-diary`)をVercelに接続する
2. 本番用のPostgreSQLを用意する(`vercel install neon`などでMarketplace経由が手軽)
3. `DATABASE_URL`・`ADMIN_PASSWORD`をVercelの環境変数に設定する
4. `prisma migrate deploy`(本番DBにマイグレーションを反映するコマンド。`migrate dev`とは別物で、対話やシード実行をせずマイグレーションSQLを適用するだけのコマンド)をどこかのタイミングで実行する必要がある(ビルド時に自動実行させるか、手動で実行するか要検討)
5. `main`ブランチにmergeしたら本番デプロイ、`develop`ブランチへのpushはPreview URLで確認、という運用が自然に噛み合いそう

## 4.5 Neon と Supabase の違い(詳細)

どちらも**別々の会社が提供する、独立したPostgreSQLホスティングサービス**。Vercelが作っているものではなく、Vercelのマーケットプレイス経由で契約・接続できるようにしているだけ、という点は共通。

### Neon

- **PostgreSQL専業**のサーバーレスDBサービス
- 特徴的な機能:
  - **データベースブランチング**: Gitのブランチのように、本番DBのスナップショットから一瞬でコピー(ブランチ)を作れる。「開発用に本番と同じデータのコピーが欲しい」「PRごとに専用のテスト用DBが欲しい」といった用途に強い
  - **自動スケーリング/ゼロへのスケール**: アクセスが無い間はDBが自動で休止し、コストを抑えられる(サーバーレスらしい特徴)
  - **読み取りレプリカ**、**ポイントインタイム復旧**(過去の任意の時点の状態に戻せる)なども提供
  - AI対応SQLクライアントや、Drizzle Studio(DB管理画面)との統合など、開発者向けツールも充実
- 無料プランがあり、そこから段階的に有料プランが用意されている(具体的な金額・容量は変わりやすいので、利用時に公式の料金ページを確認するのが確実)
- **PostgreSQLだけを、身軽に使いたい**場合に向いている

### Supabase

- PostgreSQLを中核に、**DB以外の機能もまとめて提供する統合プラットフォーム**(「オープンソース版Firebase」と呼ばれる)
- 提供機能:
  - **Postgres Database**(本体)
  - **Auth**: ユーザー認証機能(メール/パスワード、OAuthなど)を自前で作らずに使える
  - **Storage**: 画像や動画などのファイル保存機能
  - **Realtime**: DBの変更をリアルタイムにクライアントへ配信する機能
  - **Edge Functions**: サーバーレス関数
- 無料プランから開始でき($0〜)、有料プランへ段階的にアップグレードできる
- Prisma向けに`POSTGRES_PRISMA_URL`という専用の接続文字列(コネクションプーリング済み)が用意されており、Prismaとの連携も考慮されている
- **DBだけでなく、認証やファイル保存なども将来必要になりそう**な場合に向いている(今回のアプリはログイン機能が無いので、この強みはあまり活きない)

### 今回のプロジェクトにとってどちらが良さそうか

このアプリは「Prismaで直接PostgreSQLを操作するだけ」で、Supabaseの認証・ストレージ・リアルタイム機能は使う予定が無い。なので機能面ではどちらでも要件は満たせる。強いて選ぶなら:

- **シンプルにPostgresだけ使いたい・身軽さ重視** → Neon
- **将来的に認証やファイルアップロードなど他機能も欲しくなるかも** → Supabase

どちらも「Vercelとの統合が簡単」「Prismaとの相性を考慮した接続方法が用意されている」という点は共通しているので、失敗しても後から乗り換えることは可能(DBを移すこと自体は多少手間だが、`schema.prisma`のコード自体はどちらでもほぼ変更不要)。

## 6. 料金について

個人の学習・趣味プロジェクトであれば **Hobbyプラン(無料)** で十分。商用利用や独自ドメインでのチーム利用にはPro以上が必要になる場面もあるが、今回の規模なら無料枠で問題ない見込み。
