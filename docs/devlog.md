## 2026-09-08

### 調査した内容
- Next.jsの`cookies()`の仕様をドキュメントで確認(非同期API、`.set()`はServer Action/Route Handler内でしか使えない)
- `useActionState`の型エラーの原因を調査した(login関数の戻り値を型推論でしていた)
- 多層防御の仕方(errorとして返すか、redirectさせるか)

### 悩み・疑問
- Server Actionは管理画面のページを経由せず、直接POSTを送れば(curlなど)実行できてしまう。ページ側の認証チェックだけで十分か悩んだ
- パスワードのハッシュ化になぜSHA-256を選んだのか(RSAとの違い)を整理する必要があった
- ソフトデリートにしているので、削除してからまた公開させるように設計するか悩み中
- 並び替えをリアルタイム(onChange)でやったが意味あったのか

### 学習した内容
- Server Actionは独立したエンドポイントなので、呼び出し元がどこであれ実行される。ページ側の認証チェックだけでは不十分で、Action自身の中でも認証確認が必要(多層防御)
- `useActionState`は、渡す関数の「引数の型」と「戻り値の型」を一致させる必要があり、ズレるとTypeScriptの型エラーになる
- SHA-256は一方向のハッシュ関数で、RSAのような「元に戻せる暗号化」とは目的が違う。パスワードを復元不可能な形でCookieに持たせたい今回はハッシュが適切
- 多層防御の仕方は正解はないが、理由がある設計方法にする（今回は不正な入力になる可能性のものをerrorとして返している）

### 設計
- 認証用のテーブルは作らずCookie+環境変数の照合だけで済ませる
- Cookieには平文パスワードではなくSHA-256のハッシュ値を保存し、照合もハッシュ同士で比較する
- ログインフォームだけ`useActionState`を使うClient Componentにして、他はServer Component+Server Actionで統一する
- 認証チェックは`admin/page.tsx`(表示時)と各Server Action内(操作実行時)の両方で行う
- 編集画面は動的ルート /admin/posts/[id]/edit として実装し、findUniqueで該当投稿を取得、存在しなければnotFound()で404にする
- 編集画面でコメントの削除を追加した
- 並び替えをリアルタイムで行えるようにした

### 仕様
- 管理者はユーザー名なしの固定パスワードでログインする
- ログイン後は同じブラウザで12時間は再入力不要
- パスワードは環境変数`ADMIN_PASSWORD`で管理する
- パスワードを間違えたら画面遷移せずフォーム内にエラーメッセージを表示する
- 投稿削除はソフトデリート(`deletedAt`を立てるだけで物理削除はしない)
- 管理者は投稿一覧の「編集」リンクから、投稿のニックネーム・本文を編集できる
- 並び替えを選択したときにリアルタイムに反映されるようにしている

## 2026-09-09

### 調査した内容
- vercelについて
- NeonとNeonとSupabaseについて
- vercelを使うにあたってのコードの変更（環境構築）

### 悩み・疑問
- vercelと接続させるdbの選定(NeonとSupabase)
- vercelはdocker環境じゃないため、gitに送らないクライアントとかをどうするか
- PreviewとProductionでDBを共有するか分離するか
- returnの中でreturn(<ul>の中<li>の情報をreturnでまとめて返すみたいな感じ)のコードにするか、見やすさ重視のコードにするか
- 名前を入れなかった人をJSXで名無しと表示しているが検索で名無しを調べられないから許容かどうか

### 学習した内容
- ビルド→nectjsからjsに変換、効率よく読み込めるようになんかする(バンドル)
- デプロイ→ビルドでできた完成品をインターネットのサーバーにおく。ここまでの作業はgithubにpushした時点でvercel側がやっている
- envの情報をgithubは持っていないため、その情報をvercelに渡す作業が必要
- NeonはprosgresSQLのdbサービスで簡易的な操作が可能。gitのような動きができる(コミットやブランチみたいな)
- SupabaseはprosgresSQL専用ではなく総合dbサービス。メリットはユーザー認証の雛形があるや画像や動画を保存できる
- 元々PreviewとProductionでDBを共有するつもりだったが、Neonの機能でPreviewだけ自動的に専用DBブランチを持たせることができたのでそれを採用

### 設計
- 本番用DBはローカル(Docker)とは別に、Neonを用意する
- Vercelのdevelopブランチ→Preview環境、mainブランチ→Production環境、という対応にして今の運用と揃える
- まずはGit連携を試すだけにして、確認後は連携を切る(デプロイ回数を抑えるため)
- ReactionTypeマスタデータはNeonのSQL Editorから手動で投入する運用にした
INSERT INTO "ReactionType" (name, emoji) VALUES
  ('いいね', '👍'),
  ('わかる', '🙌'),
  ('ほっこり', '🥰');

### 仕様
- 個人開発規模なのでVercel Hobby(無料・非商用利用)の範囲で運用する
- 環境変数(DATABASE_URL・ADMIN_PASSWORD)はVercel側にも別途設定する必要がある
- mainブランチ=Production、developブランチ=Preview(専用DBブランチ)という対応

## 2026-09-10

### 調査した内容
- 検索での名無しさん(db上のnull)をどうヒットさせるか
- Tailwind CSSについて
- vercelとローカルの挙動の違い

### 悩み・疑問
- yamlに環境設定をそのまま書いている
- dbのデフォルトでnullを名無しさんすることは可能、しかし編集(updete)でデフォルトが反応しないため実装したいならコード上で行う必要あり
- dbではなくそもそも名無しさんを検索した時にnullをヒットさせる方法もあるが、その場合「名無し」で入力したときなどの部分検索ができない、又は全通りを書く必要がある
- エラー処理がvercelだと思った通りにできてない(エラーを投げるとおそらくnectjsのデフォエラー画面)
- 編集にはそもそも文字制限を設けていなかったため

### 学習した内容
- どちらもデメリットが存在するため、部分検索ができる方(dbで名無しさんを入力)を採用する
- db上でトリガーを使えばできるが、db上でifのような動きは分かりづらくなるため今回は不採用
- nextjsの復習
- Tailwind CSSの細かな設定を色々調べた
- おそらく見えない文字がvercelの入力欄に入っていたからなはず

### 設計
- envファイルにPOSTGRES_PASSWORDなどを追加（セキュリティ）
- env.exampleファイルに雛形を載せている
- 入力時にニックネームをnullにするとdbで「名無しさん」が入るようにする
- 編集に文字制限を設けた(dbと同じ140文字)

### 仕様
- env.exampleファイルはgitに公開しても問題ないローカルの情報と仮のURLとpasswordを入れている
- updateの際にニックネームをnullに変更した場合、コード上で判断しdbに明示的に名無しさんを入れる
- 見えない文字が入らないようバリデーション前にtrim()を入れるようにした
